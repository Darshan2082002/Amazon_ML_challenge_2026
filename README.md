
# Entity Resolution / Record Linkage Project

## 1. Project Overview

This project builds an **Entity Resolution (ER) / Record Linkage**
pipeline for identifying records from multiple data sources that refer
to the same real-world business/entity.

The project works with three source datasets:

-   `Source 1`
-   `Source 2`
-   `Source 3`

The central problem is that the same business may appear differently
across sources.

Example:

``` text
Source 1: Acme Robotics Inc.
Source 2: ACME Robotics Incorporated
Source 3: Acme Robotics
```

These records may represent the same real-world entity even though the
names are not identical.

The system therefore follows this pipeline:

``` text
Raw Data
   ↓
Data Understanding
   ↓
Preprocessing / Normalization
   ↓
Blocking
   ↓
Candidate Pairs
   ↓
Similarity / Feature Generation
   ↓
Record Matching
   ↓
MATCH / NON-MATCH / UNCERTAIN
   ↓
Entity Mapping
   ↓
Evaluation
   ↓
Final Output / Visualization
```

------------------------------------------------------------------------

# 2. Project Goal

The goal is **not simply to find similar names**.

The goal is to efficiently determine:

> Which records across different data sources represent the same
> real-world entity?

The system must balance:

1.  **Accuracy** --- avoid incorrect entity merges.
2.  **Recall** --- avoid missing genuine matches.
3.  **Efficiency** --- avoid comparing every record against every other
    record.

# 8. Member 1 --- Blocking Module

## Objective

Reduce the number of comparisons that Member 2 has to perform.

Without blocking, the system could compare every Source 1 record against
every Source 2 and Source 3 record.

The total possible comparisons are:

``` text
Number of S1 records × (Number of S2 records + Number of S3 records)
```

This can become very expensive.

Blocking creates smaller groups of potentially related records.

------------------------------------------------------------------------

## Current baseline blocking strategy

The current implementation uses:

``` text
Country + first 4 characters of normalized business name
```

Example:

``` text
Business name:
Acme Robotics Inc.

After normalization:
acme robotics

Country:
usa

Blocking key:
usa_acme
```

Another record such as:

``` text
Acme Robotics Corporation
```

can generate the same blocking key.

Those records become candidate pairs.

------------------------------------------------------------------------

# 10. Important Blocking Metrics

Member 1 must report at least:

## Blocking Recall

Blocking recall measures how many true links survive the blocking stage.

``` text
Blocking Recall =
True matching pairs found by blocking
/
Total true matching pairs
```

This is extremely important.

If the true match never enters the candidate set, the downstream
matching model cannot recover it.

Therefore:

``` text
Blocking Recall
        ↓
Upper limit on downstream pair-matching recall
```

------------------------------------------------------------------------

## Candidate Pairs

Count how many candidate pairs are generated.

Example:

``` text
Candidate pairs generated: 250,000
```

------------------------------------------------------------------------

## Reduction Ratio

A common definition is:

``` text
Reduction Ratio =
1 - Candidate Pairs / Total Possible Pairs
```

A higher reduction means fewer comparisons are required.

However, reduction must always be considered together with blocking
recall.

A blocking strategy that removes almost all comparisons but also removes
many true matches is not useful.

------------------------------------------------------------------------

# 11. Baseline Blocking → Improved Blocking

Do not immediately replace the current blocking strategy.

First run the baseline and record:

``` text
Total true links
True links found
Blocking recall
Candidate pairs
Reduction ratio
```

Then experiment with alternative blocking keys.

Possible future strategies:

``` text
Country + first 4 name characters
Country + first 5 name characters
Country + city
Country + name token
Country + address token
Multiple blocking keys
```

A strong approach may use multiple blocking rules and take the union of
their candidate pairs.

Example:

``` text
Blocking Rule 1
       ↓
Candidate Set 1

Blocking Rule 2
       ↓
Candidate Set 2

Blocking Rule 3
       ↓
Candidate Set 3

       ↓
Union / Deduplication
       ↓
Final Candidate Set
```

Compare the methods using blocking recall and reduction ratio.

# 12. Member 2 --- Matching Module

Member 2 starts only after Member 1 has produced a valid:

``` text
output/candidate_pairs.tsv
```

The matching module should compare each candidate pair.

Potential features include:

### Name similarity

Possible methods:

-   Exact match
-   Levenshtein similarity
-   Jaro-Winkler
-   Token similarity
-   TF-IDF/cosine similarity

### Address similarity

Possible methods:

-   Exact address match
-   Token similarity
-   Character similarity
-   City/state matching

### Other features

Depending on the available columns:

``` text
country_match
city_match
postal_code_match
phone_similarity
email_similarity
website_similarity
address_similarity
name_similarity
```

Only use fields that actually exist in the datasets.

------------------------------------------------------------------------

# 13. Matching Baseline

Before using ML, implement a simple rule-based baseline.

Conceptually:

``` text
High name similarity
+
High address similarity
        ↓
MATCH
```

and:

``` text
Low similarity
        ↓
NON-MATCH
```

Intermediate cases can be:

``` text
UNCERTAIN
```

The exact thresholds should be selected using the training/validation
data rather than assumed arbitrarily.

------------------------------------------------------------------------

# 14. ML Matching

After the baseline, Member 2 can train a classifier.

Possible models:

``` text
Logistic Regression
Random Forest
XGBoost
LightGBM
```

The model input should consist of pair-level features.

Example:

``` text
name_similarity
address_similarity
country_match
city_match
postal_code_match
...
```

Output:

``` text
match_probability
```

Then convert the probability into:

``` text
MATCH
NON-MATCH
UNCERTAIN
```

using thresholds selected from validation experiments.

------------------------------------------------------------------------

# 15. Member 3 --- Evaluation

Member 3 should evaluate both:

``` text
Baseline matcher
        vs
ML matcher
```

Important metrics:

``` text
Precision
Recall
F1-score
```

For entity resolution, precision and recall are especially important
because:

-   False positives can incorrectly merge different businesses.
-   False negatives can leave the same business split across multiple
    entities.

------------------------------------------------------------------------

# 16. Error Analysis

Do not report only a single F1 score.

Inspect examples of:

### True positive

Two records are correctly identified as the same entity.

### False positive

Two different businesses are incorrectly matched.

### False negative

Two records referring to the same business are incorrectly separated.

### Uncertain cases

Records where available evidence is insufficient.

Create an error-analysis table:

``` text
S1_ID
Candidate_ID
True_Label
Predicted_Label
Name_Similarity
Address_Similarity
Model_Probability
Error_Type
Reason
```

This will help explain model behavior in the final presentation.

------------------------------------------------------------------------

# 17. Final Entity Mapping

The final output should associate records with a common entity ID.

Example:

``` text
Entity_ID | Source | Record_ID | Business_Name
------------------------------------------------
E001      | S1     | S1-001    | Acme Robotics Inc.
E001      | S2     | S2-104    | Acme Robotics
E001      | S3     | S3-982    | Acme Robotics Ltd
E002      | S1     | S1-002    | Acme Bakery
E002      | S2     | S2-205    | Acme Bakery LLC
```

This is the final purpose of the entity-resolution pipeline.
